Beispielanwendungen für den Schul-Keycloak `auth-dev.htl-leonding.ac.at`.
Sie laufen auf `localhost` und melden sich am *echten* Server mit *echten*
Schulkonten an — keine Attrappe, kein lokaler Keycloak.

== Schnellstart

[source,bash]
----
# Fenster 1 — Backend
cd backend-quarkus && ./mvnw quarkus:dev

# Fenster 2 — Frontend ohne Framework (Stufen 1–5)
cd frontend-vanilla && python3 -m http.server 8000

# oder: Angular-Frontend (Stufen 1–3)
cd frontend-angular && npm install && npm start
----

Dann `http://localhost:8000` öffnen und auf *Anmelden* klicken.

Für Stufe 5 braucht das Backend zusätzlich das Secret seines Dienstkontos:

[source,bash]
----
# in backend-quarkus/.env — per .gitignore ausgeschlossen
KC_DEMO_BACKEND_SECRET=$(security find-generic-password -a demo-backend -s kc-htl-leonding-demo-backend -w)
----

Ohne die Variable laufen die Stufen 1–4 unverändert; nur `/api/groups` meldet
dann `502` mit dem Hinweis, dass das Dienstkonto sich nicht anmelden konnte.

IMPORTANT: Der Port ist nicht beliebig. `8000`, `4200` und `5173` sind die
Weiterleitungsziele, die am Client `demo-frontend` eingetragen sind. Keycloak
vergleicht sie als Text — ein anderer Port ergibt `Invalid parameter: redirect_uri`.

== Die fünf Stufen

[cols="1,3,2",options="header"]
|===
|Stufe |Was sie zeigt |Wo

|1
|Anmelden und abmelden, Authorization Code Flow mit PKCE
|`frontend-vanilla/index.html`, `frontend-angular/`

|2
|Was im Token steht — und dass es jeder lesen kann
|dieselbe Datei, Anzeige „Claims"; auch im Angular-Frontend

|3
|Geschützter Endpunkt, Token wird serverseitig geprüft
|`/api/protected`, in beiden Frontends

|4
|Autorisierung über Klassengruppe und über Rolle
|`/api/my-class`, `/api/teachers-only`

|5
|Gruppen auflisten, Mitglieder anzeigen — *Dienstkonto* plus Bezugsprüfung
|`/api/groups`, `/api/groups/{id}/members`
|===

== Was hier zu lernen ist

=== Ein Token ist nicht geheim, seine Signatur ist der Punkt

Der Mittelteil eines JWT ist Base64, nicht Verschlüsselung. Die Demo zeigt ihn
deshalb offen an. Was zählt, ist die *Signatur* — und die prüft das Backend,
nicht der Browser.

=== `aud` ist die Zeile, die zählt

Getrennte Clients je Projekt allein verhindern nichts. Ohne
`quarkus.oidc.token.audience` nähme das Backend jedes gültige Token dieses
Realms an — auch eines aus einem fremden Projekt, denn die Signatur stimmt ja.
Erst der Zielgruppen-Mapper am Frontend plus die Prüfung am Backend ergeben die
Grenze.

=== 401 und 403 sind verschiedene Fehler

`401` heißt „kein gültiges Token". `403` heißt „gültiges Token, aber die Rolle
fehlt". Die Demo zeigt den Statuscode deshalb immer mit an.

=== PKCE ohne Bibliothek

Rund dreißig Zeilen mit der Web Crypto API. Ein öffentlicher Client kann kein
Geheimnis aufbewahren — der Quelltext liegt im Browser. PKCE löst das, indem
beim Start ein Zufallswert erzeugt und nur dessen Hash mitgeschickt wird.

NOTE: `response_type=token` (Implicit) und `code_challenge_method=plain` lehnt
der Server ab — nicht der Client. Die Client Policies des Realms machen beides
serverseitig unmöglich. Ausprobieren lohnt sich: Die Fehlermeldung kommt von
Keycloak.

=== Rollen kommen nicht aus `groups`

Die Zeile, die eine Stunde gekostet hat:

[source,properties]
----
quarkus.oidc.roles.role-claim-path=realm_access/roles
----

Ohne sie sucht Quarkus die Rollen zuerst im `groups`-Claim und hört auf, sobald
der nicht leer ist. In diesem Realm steht dort die *Klasse*. `@RolesAllowed("teacher")`
antwortet dann mit `403`, obwohl die Rolle im Token steht.

Tückisch daran ist die Zeitfolge: Vor der Einführung der Klassengruppen hätte
derselbe Code funktioniert.

=== Rollenprüfung reicht nicht — die meisten Fragen sind Bezugsfragen

Stufe 4 fragt „welche Rolle hat diese Person". Stufe 5 fragt „darf diese Person
*diesen* Datensatz sehen" — und die Antwort hängt an beidem, am Aufrufer und am
angefragten Objekt.

[cols="1,2",options="header"]
|===
|Aufrufer |`/api/groups/<id>/members`

|Lehrkraft (Rolle `teacher`)
|jede Gruppe

|alle anderen
|nur Gruppen, in denen sie selbst Mitglied sind — also die eigene Klasse

|lokales Konto ohne `groups`
|keine Gruppe. Kein Fehler, kein Sonderfall
|===

IMPORTANT: Der Gruppenpfad für den Vergleich kommt vom *Server*
(`GET /groups/{id}`), nicht aus der Anfrage. Wer den Pfad mitschicken darf,
stellt sich seine Berechtigung selbst aus. Der Aufrufer nennt nur die ID.

Verglichen wird gegen den `groups`-Claim des Tokens — er ist signiert. Ein
zweiter Aufruf beim Server ergäbe denselben Wert, nur langsamer.

=== Erneuerung ist der Teil, den Bibliotheken verstecken

Fünf Minuten Tokenlebensdauer heißt: Jede Anwendung braucht Erneuerung, nicht nur
langlaufende. Im Vanilla-Frontend steht sie offen da — rund dreißig Zeilen:

* *Vor* dem Aufruf prüfen, nicht nach einem `401` wiederholen. Ein
  Wiederholungsversuch verdoppelt alles, was der erste Aufruf schon ausgeführt
  hat, bevor er am Token scheiterte.
* Dreißig Sekunden Vorlauf, damit ein Token nicht *während* des Netzwegs abläuft.
  Dieser Fehler ist sonst nicht reproduzierbar.
* Ein laufender Tausch wird geteilt, nicht wiederholt. Ohne diese Sperre starten
  drei gleichzeitige Aufrufe drei Erneuerungen mit demselben `refresh_token` —
  und sobald der Realm Refresh-Token-Rotation einschaltet, entwertet der erste
  Tausch die anderen beiden. Der Fehler tritt dann erst unter Last auf und sieht
  aus wie ein Serverproblem.

NOTE: Das `refresh_token` ist kein Client-Geheimnis. Der Tausch geht ohne
`client_secret` — der Client ist öffentlich, und die Bindung stellt Keycloak über
`client_id` her.

=== Was die Bibliothek abnimmt — und was sie nicht abnimmt

Das Angular-Frontend macht dieselben drei Stufen wie das Vanilla-Frontend, nur
mit `angular-auth-oidc-client`. Der Vergleich ist der eigentliche Zweck:

[cols="2,3,3",options="header"]
|===
|Schritt |ohne Framework |mit Bibliothek

|PKCE
|rund dreißig Zeilen Web Crypto
|`responseType: 'code'` — den Rest macht sie

|Rückkehr vom Anmeldeserver
|Code aus der Adresszeile lesen, `state` prüfen, tauschen
|`checkAuth()` beim Start

|Erneuerung
|dreißig Zeilen mit Vorlauf und geteiltem Tausch
|`silentRenew`, `useRefreshToken`, `renewTimeBeforeTokenExpiresInSeconds`

|Token an Aufrufe hängen
|von Hand je `fetch`
|`authInterceptor()` plus `secureRoutes`
|===

Was sie *nicht* abnimmt, und das ist die Zeile, die hängen bleiben soll:

* Der *Server* prüft Weiterleitungsziel, PKCE und Zielgruppe. Die Client
  Policies des Realms lehnen impliziten Ablauf und `plain` ab — unabhängig
  davon, was der Client schickt.
* Das *Backend* prüft die Signatur und `aud`. Ein Frontend kann sich keine
  Berechtigung ausstellen, egal welche Bibliothek es benutzt.
* `secureRoutes` ist eine Sicherheitsentscheidung, keine Bequemlichkeit: Ohne
  diese Liste hinge der Interceptor das Token an *jeden* Aufruf, den die App
  macht — auch an fremde Hosts.

Anders gesagt: Die Bibliothek nimmt Arbeit ab, keine Verantwortung. Wer beide
Frontends nebeneinander laufen lässt, sieht dieselben Statuscodes.

=== Stufe 5 ist die einzige Stufe mit einem Geheimnis

Klasse und Rolle der *angemeldeten* Person stehen im Token — dafür ist kein
einziger Aufruf beim Server nötig. Erst wer etwas über Personen wissen muss, die
gerade *nicht* angemeldet sind, braucht ein Dienstkonto.

An dessen Secret hängt die Sicht auf alle Konten des Realms. Deshalb bekommt es
nicht jedes Projekt, sondern nur benannte — siehe D36 im Infrastruktur-Repo.

== Stand

Was *geprüft* ist (2026-08-22, gegen den laufenden Server, im Browser):

[source,text]
----
/api/public          ohne Token                 200
/api/protected       ohne Token / Unsinn-Token  401
/api/protected       als Lehrkraft              200, roles [teacher, ...], groups [/staff/teachers]
/api/my-class        als demo.tester            200, class "", Hinweis statt Fehler
/api/teachers-only   als Lehrkraft              200
/api/teachers-only   als demo.tester            403
CORS-Vorabfrage von http://localhost:8000       200, allow-origin gesetzt
----

Die beiden Zeilen zu `/api/teachers-only` gehören zusammen: Erst `200` **und**
`403` zusammen belegen, dass die Rolle trennt statt durchzuwinken.

Stufe 5, gegen den Server gelaufen (2026-08-23): Gruppen laden und Mitglieder
anzeigen funktionieren mit dem Dienstkonto des Clients `demo-backend`.

Was *noch nicht* geprüft ist:

* *Die Bezugsprüfung aus der Sicht einer Schülerin* — dass eine fremde Klasse
  `403` liefert und die eigene `200`. Bisher nur aus Lehrkraft-Sicht gesehen,
  und die kommt am ersten Zweig vorbei.
* *Das Angular-Frontend im Browser.* Gebaut (2026-08-23, Angular 22.1.3,
  `angular-auth-oidc-client` 22.0.0); `ng build` läuft durch und der
  Entwicklungsserver antwortet auf `4200`. Eine *Anmeldung* ist damit nicht
  belegt — dass ein Bündel übersetzt, sagt nichts über den Ablauf. Zu messen
  sind dieselben drei Zeilen wie beim Vanilla-Frontend: Anmelden, Claims
  sichtbar, `/api/public` `200` und `/api/protected` `401` vor der Anmeldung
  bzw. `200` danach.

Das Token läuft nach *fünf Minuten* ab (`accessTokenLifespan=300`). Das Frontend
erneuert es seit dem 2026-08-23 selbst — die Statuszeile zeigt die Restlaufzeit
mit, und beim nächsten Aufruf nach Ablauf wird still getauscht. Nach *dreißig
Minuten* ohne Aktivität endet die Sitzung im Keycloak; dann hilft nur neu
anmelden, und die Demo sagt das auch.

== Aufbau

[source,text]
----
backend-quarkus/    Quarkus 3.38.3, Java 25 — prüft Tokens; meldet sich nur für
                    Stufe 5 selbst an, und dann als Dienstkonto
frontend-vanilla/   eine HTML-Datei, kein Build, PKCE von Hand — Stufen 1–5
frontend-angular/   Angular 22 + angular-auth-oidc-client 22 — Stufen 1–3
----

Beide Frontends benutzen dasselbe Backend und denselben Client `demo-frontend` —
das ist der Grund, warum die Demos in *einem* Repository liegen und nicht in
dreien. Ein Client hat eine *Liste* von Weiterleitungszielen; `8000`, `4200` und
`5173` stehen alle drei darin. Ein eigener Client je Frontend wäre eine falsche
Grenze: Getrennt werden *Projekte*, nicht zwei Oberflächen desselben Projekts.

CAUTION: Das Angular-CLI verlangt Node `>= 22.22.3`, `>= 24.15` oder `>= 26`.
`frontend-angular/.nvmrc` nennt 24 — mit nvm genügt `nvm install 24 && nvm use`.
Auf einem älteren Node bricht schon `npm start` ab, mit einer Meldung über die
Node-Version und nicht über Angular.
